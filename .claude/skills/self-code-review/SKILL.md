# self-code-review（コミット前の自己レビュー）

コミットを作る前に、**ステージ済み差分（`git diff --staged`）の追加行**に対して
以下を上から順に確認し、違反を修正してからコミットする。
委譲されたエージェントも、コミットを作る場合はこのチェックを必ず実施する。

## 1. コメント規約

原則: **コードは How ／ テストコードは What ／ コミットログは Why ／ コメントは Why not**。
コメントに書けるのは「なぜ別のやり方にしないか」「コードから読めない制約・不変条件」だけ。

アンチパターン（見つけたら削除または書き換え）:

- **What の説明**: コード・名前の言い換え、対象の説明（「〜を返す」「〜のラベル」）、
  セクション見出し的な区切りコメント
- **利用される箇所の事情**: 「〜に使う」「〜が使う」「呼び出し側は〜する」「〜側でこう表示する
  ため」「〜（呼び出し元名）経由」等の呼び出し側の都合。**対象自身の契約として書き直せるなら
  書き直し、書き直せないなら削除**（例:「呼び出し側はその間サーバー解析へ向かう」→
  「準備状態は state で公開する」）。フォント・色・記号の形などデザイン・レイアウト側の
  情報を文言定数等にコメントするのも同類
- **陳腐化する当時の判断・経緯**: 「〜との指摘で廃止」「旧実装では」「モック通り」
  「承認済み」「検証済み」「〜予定」「ベータでは」、コミットSHA・タスク名・
  他ファイル/クラス名への参照（責務の委譲先を示す参照は可・利用側を示す参照は不可）
- **利用側文脈の命名**: fallback・demo等、その部品をどう使うかを表す語をクラス名・
  ファイル名・変数名に入れない（切替ポリシー等を持つ合成箇所の命名のみ可）

匂いワードでの機械的な洗い出し（ヒットしたら精査）:

```bash
git diff --staged | grep -nE "^\+.*(//|/\*|\*|#|<!--).*(に使う|が使う|呼び出し側|利用側|画面側|から呼ばれる|参照|旧|指摘|予定|ベータ|と同じ|承認済み|検証済み|モック|例:)"
```

（1本のgrepで書くこと。2段パイプにすると1段目の`-n`が付ける行番号プレフィックスで
2段目の`^\+`が永遠にマッチしなくなる——実際にこの形で長期間すり抜けていた）

## 2. コミット対象の混入チェック

- git管理外の作業ログ置き場（リポジトリ直下のローカル作業ディレクトリ）への参照が
  含まれていない（壊れたリンクになる。pre-commitフックも機械ブロックする）
- 秘密・実値（トークン・パスワード・実名・実プロジェクト番号の例示）が含まれていない
- ビルド成果物・巨大バイナリ・git管理外にすべきローカル設定が `git add` に紛れていない

## 3. ユーザー向け文言

- 追加・変更した文言は docs/wording.md（文言表）に照合する。表に反する語はフラグ、
  新しい揺れは決めてから表に行を追加する
- wording.mdの表記・スタイル節の禁止事項に触れていない
- ユーザー向け文言に文字の「▶」を使っていない（iOSで絵文字レンダリングされる。
  再生・実行系の表現はアイコンで統一する）

## 4. UI・ビジュアル

- UI変更を含むなら DESIGN.md に照合する（三色体系・No-jitter原則・アンチパターン）。
  逸脱はmiyadoさんの明示的な承認がない限り不可

## 5. コミットの形

- 機能単位で分割されている（無関係な変更が混ざっていない）
- メッセージ: 件名=何を、本文=Why（なぜこの変更・なぜこのやり方）。
  「何をやったか」の詳細列挙はdiffが語るので書かない
