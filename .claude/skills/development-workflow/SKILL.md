# 開発手順

以下のパスはリポジトリルートを基準とする。
依頼された範囲で調査・実装・検証を進め、メンテナには判断材料を揃えて相談する。
このスキルの利用自体は、push・デプロイ・公開などの追加の許可にはならない。

## 1. 現在地と完了条件

- セッション開始時の引き継ぎ、作業差分、ブランチ、関連する既存Issueを確認する。他の作業の差分を混ぜない。
- 調査・レビュー・実装・リリースのどこまでが依頼かを確認する。レビューのみなら問題・根拠・修正方針を提示する。
- 利用者が行う操作と期待する結果で完了条件を整理する。対象プラットフォーム、保存・復元、失敗時の振る舞いも変更に応じて含める。
- 調査で解決できることは先に調べる。仕様判断が必要な点は選択肢と影響を示し、依存しない作業を進めながらIssue・機能ごとにまとめる。

## 2. 不確実性を先に検証する

- 精度・性能・エンジンなど採用可否が不確かな変更は、採用条件と比較方法を先に決め、再現できる実験で評価する。結果を見てから基準を都合よく変えない。
- 採用しない実装をアプリへ残さない。再利用できる研究資料・検証データは研究側へ残す。
- API・DB・保存形式の変更は、設計時に旧アプリ・既存データ・新旧混在への影響を確認する。新経路のテスト成功だけで移行可能と判断しない。

## 3. UI変更はモックで方針を確定する

1. `DESIGN.md` と `docs/wording.md` を読み、目的・操作・表示情報を整理する。
2. **製品コードのUI実装前に、見て判断できるモックをメンテナへ提示する。** 画像、HTMLなど変更に適した形式を使い、コードや文章の説明だけで済ませない。必要に応じて遷移、読み込み中・空・エラー状態も示す。
3. 調整を反映し、メンテナの明示的な回答で方針を確定する。返答待ちや沈黙を合意に置き換えず、確定前に対象UIを実装しない。独立した調査・互換性確認などは進めてよい。
4. 確定したモックの画面構成と操作を実装する。外観は現行アプリのデザイン・既存部品・`DESIGN.md`を基準にし、モック固有の見た目を持ち込まない。すでに当該モック・方針が明示的に承認されている場合は確認を繰り返さない。
5. 実装中に見た目や操作の未決事項・方針変更が生じたら、該当箇所のモックを更新して確認する。実装後は実画面・操作をモックと照合する。

モック段階からデザインと文言の規約に従う。設計として継続利用する成果物は `docs/` に置く。

## 4. 機能単位で実装・検証する

- 確認できる機能単位で、操作から保存・復元まで通して実装する。大きな未検証差分を溜め込まない。
- 不具合は再現条件と原因を確認して直す。再試行で別のエラーになったら、新しい原因と次の対応を伝える。
- 共通コードの変更は各プラットフォームの利用箇所まで確認する。共有状態や非同期処理が他機能へ与える影響を見る。
- ロジックは期待結果・境界条件・再発防止を検証する。保存・同期では変更に応じて、再起動、復元、重複再送、通信断、削除後の遅延要求、アカウント切替を確認する。
- 影響するプラットフォームのビルド・テストを行う。UIはVRTに加え表示と操作、エンジンは実バイナリの起動・解析結果・速度を確認する。修正後は影響する検証をやり直す。
- ビルド、インストール、起動、操作確認の成功を区別する。未実施の実機・本番確認を完了扱いしない。
- ストア画像は実際の棋譜・解析結果と整合させ、生成後に目で確認する。

## 5. レビュー・コミット・リリース

- コミット前は `.claude/skills/self-code-review/SKILL.md` に従う。レビュー指摘の修正後に必要な検証を再実行する。
- 機能単位でコミットし、本文に変更理由を残す。設計資料は `docs/`、一時ログは管理外の作業場所へ分け、コミット対象の文書から管理外ファイルへリンクしない。
- リリース依頼時は `app/docs/release-checklist.md` を読む。対象範囲はメンテナが決め、pushは明示許可に従う。既存の許可を尊重し、許可済み操作の確認を繰り返さない。
- デプロイ・提出後はサービス側の状態を確認する。コマンドの終了だけを成功の根拠にしない。

## 6. 報告と引き継ぎ

実装済み、検証済み、未確認・未完了、コミット・push・本番反映・審査提出・公開を区別して報告する。
変更の効果、検証結果、残る判断と次の一手を簡潔に示し、引き継ぎへ残す。
一部の検証成功を機能全体やリリースの完了と言い換えない。
