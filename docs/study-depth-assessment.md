# 検討を深くする前提調査（#102）

以下の `/path/to/` は、別途用意する入力・出力先の例です。個別棋譜を含む生データは同梱していません。

確認日: 2026-09-27。対象: [research #102](https://github.com/hmiyado/shogi-supplement-research/issues/102)。
課金の実装、強条件の正式採用、本番の条件・クォータ変更は含めない。

## 結論

現行の解析・ドリル二次判定は40万ノードのまま維持する。
検討を400万ノードにすれば食い違いが小さい、という仮説は今回の標本では支持できない。
抽出済み悪手候補の16.17%で悪手→非悪手になった。これは40万側の誤答率ではなく、
深さによる判定の変化率である。400万側も正解ラベルではない。

提案は「強い検討の販売を開始せず、独立した検討条件として内部検証を続ける」。
採用基準の承認や、正式な有料プラン・価格・予算の決定を済ませたという意味ではない。

| Issueの項目 | 調査結果 |
| --- | --- |
| 二次判定の分離 | 実装済み。検討条件を受け取らない `DrillEvaluationEngine` と固定条件を検証 |
| ねじれ率 | 1,670局面の既存測定を現行判定で再集計し、過去の集計と完全一致 |
| ノード数の統一 | Android/iOS/Web/サーバーは40万を既定値とする。WASMは可変nodesを受け付けず固定 |
| WASMを強くできるか | ノード増量とpthread化は別問題。iOSカスタムスキームのヘッダー追加だけではpthreadの前提を満たさない |
| サーバー条件と予算 | 下記に設計を整理。現行サービスへ強条件や予算台帳を導入していない |

## 条件分離の検証

`InvariantDrillEngine` は探索前に `newGame()` を呼び、40万ノード・MultiPV=2を指定する。
`DrillSecondaryJudgeTest.strongerStudyDoesNotChangeSecondaryJudgementOrItsConditions` は、
400万・MultiPV=3の検討を間に挟んでも、同じ問題・指し手の二次判定結果が変わらず、
探索履歴がリセットされることを検証する。WASMは `purpose=drill` の際に条件を固定し、
サーバーもクライアントのMultiPV指定よりドリルの固定条件を優先する。

これは指定条件・履歴分離の回帰保証であり、異なるCPUやエンジン版での完全一致の証明ではない。
エンジン版・評価関数の採用変更は #101、保存結果の版管理・再解析は #87 の責務である。

再実行した検証:

- `:analysis:jvmTest` 300件、`:engine:remote:jvmTest` 80件、`:server:worker:test` 117件: 成功。
- `node --test engine-wasm/study_worker_test.mjs`: 4件成功。
- `python3 tools/test_compare_drill_nodes.py`: 2件成功。
- `:analysis:summarizeDrillComparison`: 生の局面測定JSONから再集計し、既存集計JSONと完全一致。

## 40万／400万ノードの測定

2026-09-19の測定を2026-09-27に再集計した。新しく探索をやり直した結果ではない。
300対局から、出題対象となる286対局・1,670局面を抽出。各局面の着手前後を、
同じv9.40＋Háo、Threads=1、Hash=128MB、MultiPV=2、FV_SCALE=20で比較した。
毎探索 `isready/readyok/usinewgame`、初期局面からの全指し手履歴を渡した。

| 指標 | 全1,670局面 | 前後・両条件のPV1がすべて非boundの818局面 |
| --- | ---: | ---: |
| 最善手一致 | 1,345 / 80.54% | 666 / 81.42% |
| 悪手→非悪手 | 270 / 16.17% | 161 / 19.68% |
| 分類変更 | 618 / 37.01% | 279 / 34.11% |
| 着手前CP絶対差 中央値 / p95 | 127 / 521.2 | 151 / 543.65 |
| 着手後CP絶対差 中央値 / p95 | 145 / 459.2 | 146.5 / 418.65 |

CP差は4端点ともCP型の組のみ（全体1,213組、非bound448組）。詰みをCP差に混ぜない。
CP型でも極端な値があるため平均だけでは判断しない。分布は
[集計データ](verification/study-depth-measurement.json)に保存した。

着手前＋着手後の探索時間は40万が中央値1.022秒/p95 1.155秒、400万が10.312秒/11.561秒。
macOS arm64でのgo〜bestmoveの合計であり、端末での操作待ち時間やサーバー費用ではない。

制約:

- 悪手候補に限定した標本なので、通常の局面全体に対する頻度ではない。
- 元標本は先手の棋力帯による抽出。両側の候補を扱うが、母集団を均等に代表しない。
- 同一対局内の相関があり、1,670件を独立試行とする信頼区間は付けない。
- boundを含む最終出力と非bound集合は分ける。非boundも真の局面価値を保証しない。
- 「ねじれが小さい」の数値基準は合意されていない。今回の16〜20%を問題なしと扱わない。

対象JSON・runner・エンジン・評価関数のSHAは集計データのmanifestに保持。
生データは `/path/to/depth-measurement/`、対象は `/path/to/positions.json`。
一時領域の生データはGitに含まれないため、別環境での再集計には別途保管した同じデータが必要。

## WASM: 隔離条件と中断

[Emscriptenのpthread要件](https://emscripten.org/docs/porting/pthreads.html)では、
共有メモリを使えるクロスオリジン隔離が必要になる。
ヘッダー文字列を付けたことと、実行環境で隔離が成立したことは区別する。

`tools/study-isolation-probe/` の専用ページで `crossOriginIsolated`、SharedArrayBuffer、
共有WebAssembly.Memoryを実測した。iOSは26.5シミュレータのWKWebView、Chromiumはローカルの
Playwrightで確認した。製品アプリの非公開設定や追加entitlementは使っていない。

| 配信方法 | Chromium | iOS WKWebView |
| --- | --- | --- |
| localhost HTTP・ヘッダーなし | 共有メモリ不可 | 共有メモリ不可 |
| localhost HTTP・COOP/COEPあり | 共有メモリ可 | 共有メモリ可 |
| Service Workerによるヘッダー付与・再読込後 | 共有メモリ可 | このアプリ構成ではService Worker自体が未提供 |
| `kento://`・ヘッダーなし | 対象外 | 共有メモリ不可 |
| `kento://`・COOP/COEPあり | 対象外 | 共有メモリ不可 |

証跡: [Chromium](verification/study-isolation-chromium.json)、
[iOS](verification/study-isolation-ios.json)。iOSのUAはOS版と一致しないため、
`UIDevice.current.systemVersion`も記録した。

判断:

- GitHub Pages向けのService Worker案は原理上成立する。ただし実際のPagesへの導入、Safari、
  Firebase等の外部資産、初回リロード、キャッシュ更新との共存は未検証。今回は公開サイトを変更していない。
- 現行iOSの `KentoLocalSchemeHandler` にヘッダーを足すだけでは成立しない。
  pthread採用にはHTTP(S)配信経路などの変更が必要。実機・オフライン・ポート寿命等の検証も伴う。
- 共有メモリ可はpthreadエンジンの動作合格ではない。#101の候補バイナリ、入口、停止、メモリ、
  配布用iOSと実機の確認を別に行う。
- 今回はSafari単体を検証していない。WKWebViewの結果をその代用にはしない。

現行 `build_wasm_browser.sh` は単一スレッド版で、`callMain`中の`go nodes N`は同期処理。
Workerのイベントループに`stop`を送っても探索中には処理できず、USIの穏当な停止にはならない。
Webの`WorkerStudyEngine.quit()`はWorker破棄へ進み、途中の最善手は取得しない。
iOSの`WasmStudyEngine.quit()`は空実装で、取消時はブリッジのコールバックを解除するだけ。
バックグラウンド探索の停止は保証しない。このため「読み続けて途中の結果で止める」機能は未成立。

強条件導入前の中断契約は、requestId単位の取消、Workerのterminate、遅延応答の破棄、
待機状態の解除、次Workerの準備を一組にする。古い取消が新しい要求を止めない回帰が必要。
USI stopで途中結果を採用する方式は、pthreadまたは協調的非同期探索への変更後に別途確認する。

## OS間の説明方針

判定は「共通の解析条件で採点」、検討は「局面をさらに調べる別の解析」と説明する。
同じノード数でも速度・メモリ・実行エンジンが同等とは限らない。
「有料なら正解」「無料の判定は間違い」「全端末で同じ速さ」とは表現しない。

表示する条件は結果の `engine_meta` 由来とし、端末のプラン名や要求値から推測しない。
エンジン版・評価関数・ノード数・候補数を短い条件名から確認できるようにする。
保存済みの問題の正誤や学習履歴は、検討の条件切替だけでは変更しない。
これは文言方針であり、新しい課金画面やUI文言の実装ではない。

## サーバー条件切替・ノード予算の設計案

### 条件を決める境界

クライアントは用途と局面だけを送る。エンジンrev、評価関数、ノード数、Threads、Hash、
FV_SCALEを自由に指定できるAPIにはしない。検討のMultiPVもサーバーが許可範囲を検査する。
サーバーが検証済みの権利情報と固定プロファイル表から有効条件を選び、条件全体を保存する。
`purpose=drill`はプランと無関係に固定プロファイル。用途省略の旧要求は現行40万へ対応する。
未知の用途・プロファイルは明示エラーにし、強い設定への暗黙変換をしない。

プロファイルは変更不可のIDと全条件のハッシュを持つ。内容変更時は新IDにする。
要求受付後にプラン・設定が変わっても、受理済みジョブは固定した条件で実行する。
キャッシュにはユーザー、用途、局面＋指し手履歴、実条件ハッシュを含め、結果のengine_metaと照合する。
不明な来歴や別条件の結果を同じ結果として返さない。再解析の世代管理は#87に従う。

### 予算の単位と予約

まず1局解析の日次上限は変更せず、単発局面解析を対象にする。
既存100局面/日の設定なら、40万×100＝4,000万ノード相当を移行時の基準にできる。
これを正式な商品上限として確定したわけではない。ドリル二次判定は通常2局面を読むため
80万相当を必要とする。強検討がドリルの利用余地を奪わない配分も商品設計時に決める。
有料枠を導入する場合は検討専用の追加枠とし、ドリルの深さを増やす権利にはしない。

予算台帳は `(user_id, quota_day, pool)` とし、job/profile/reserved_nodes/stateを予約に保存する。
日界は現在のサーバーの日界と合わせてAsia/Tokyoに固定し、accepted_atからサーバーで決める。
日界や有効期限をクライアントに指定させない。数値は64bit整数、正値・加算オーバーフローを検査する。

1. 認証・用途・局面・権利を検査し、条件を確定する。
2. 同条件の完成キャッシュなら再消費なし。実行中の同一要求なら既存ジョブへ接続する。
3. DBトランザクション内でユーザーの日次予算をロックし、ジョブの一意性を再確認。
   `used + reserved + request <= limit`を満たす場合だけ予約とジョブを同時作成する。
   現行の「件数を読んでから別操作で作成」では、異なる局面の並列要求を原子的に制限できない。
4. ワーカーが一意のlease/fencing tokenでclaimし、開始時に予約を使用済みへ移す。
5. 正常・詰み等で早期終了しても、開始した探索は予約額を消費する。実ノード数・実行時間は別途記録。
   実ノード数は探索の停止判定により要求値を超え得るため、商品予算と物理的CPU上限を同一視しない。
6. 未開始の取消・ディスパッチ失敗だけ予約を返す。開始後の取消・エラー・切断では返さない。
   再接続は同じjobへ接続し、再探索が必要なら新しい予約を取る。失敗連打による無料探索を防ぐ。
7. lease失効だけで未開始と推定しない。開始が不明なら消費を維持し、古いworkerの完了書込みは
   fencing tokenで拒否する。返金・取消・完了操作は冪等にする。

HTTP切断だけで必ず計算が止まるとは扱わない。壁時計timeout・同時実行数・メモリ上限を併用する。
同じノード数でもエンジン/MultiPV/CPUによって費用が変わるため、ノード予算は利用枠の単位であり、
サーバー原価の厳密な上限ではない。Linux実機でのp95とCPU時間計測後にプロファイルを承認する。

### 旧workerとの混在と導入順

旧workerは予約台帳を更新しないため、台帳だけ導入して強条件を有効化してはいけない。
先に40万のまま全workerを予約対応へ更新し、旧API要求も同じ予約経路へ接続する。
移行中は強条件無効・旧制限維持。途中の日次切替は旧使用分を取り込むか、日界で切り替える。
全経路を確認してから内部アカウントだけで強条件を有効化する。
rollbackは新規強条件の受付を停止し、開始済み予約の精算と旧クライアントの40万経路を維持する。
台帳や新条件のキャッシュを削除して戻す手順にはしない。

必要な実装時テスト: 異なる局面の同時予約、同一要求の重複、二重完了/取消、日界、
開始前後のworker停止、旧worker遅延完了、キャッシュhit、権利変更、不正用途、
ドリル条件不変、予約超過・整数境界。今回これらの台帳実装・本番移行は行っていない。

## 次の判断

前提調査の結論は「現在の条件で強い検討をそのまま販売するには不足」。
測定結果・配信方式・停止契約・予算方式は整理できたが、強条件の正式採用は別の判断とする。
進める場合は、iOSの中断と配信方式、#101の品質/性能、原子的な予算台帳を満たした内部検証が先になる。
