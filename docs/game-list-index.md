# 棋譜一覧の索引・集計・ページ取得

Android/iOSの端末DBを対象にする。共有UIは `GameListReader` を通じて取得し、一覧表示のための `getAllGames()` と全局面再生を行わない。Webマイページは別のSupabase一覧取得経路であり、この端末DB索引の対象外。

## 保存と索引

SQLite migration 26で派生テーブルと更新トリガーを追加する。既存の棋譜・解析結果・定跡・ラベルの保存形式は変更しない。本番Supabaseへのmigrationは不要。

- `game_position_key`: 棋譜IDと局面キーのSHA-256。局面全体・先手の形・後手の形の3種類。手番は含めず、対象側の持駒は含む。本譜と保存済み検討分岐を対象にする。
- `game_list_index` / `game_opening_key`: 出典・持ち時間・戦型の正規化値。
- `position_label_index`: アカウント、ラベルエントリ、局面キーハッシュ、表示名。同名ラベルや本譜・分岐の重複で件数を増やさない。
- `game_list_pending` / `position_label_pending`: 更新トリガーで積む未処理ID。初回移行時は既存IDを積む。読み取り準備時にバックグラウンドで16棋譜・32エントリずつ処理し、同一トランザクションで索引置換とキュー消化を行う。

索引は再起動後も残る。中断時は未処理分から再開する。ラベル変更はラベル索引だけを更新し、棋譜を再生しない。棋譜の追加・手順変更は該当棋譜のみ再索引化する。削除時はトリガーで派生行も除去する。

## 読み取り

- 本文は40件ずつ。`analyzed_at DESC, id DESC` のカーソルで次ページを取得する。同時刻の棋譜をIDで順序づけ、OFFSETの深い走査を避ける。
- 件数・勝率・悪手率はSQLで全フィルタ対象を集計する。推定棋力だけは対象のrating列を取得し、既存の推定方法を維持する。
- 保存した条件の件数、期間比較、フィルタ候補は読込済みページ数に依存しない。該当棋譜がない既知ラベルも候補として保持する。
- カードのラベルはページの返却時に揃える。ラベルだけを後から追加しない。
- DB変更通知、アカウント・条件変更で一覧を再取得し、旧要求の結果を新しい条件へ混ぜない。読み取り失敗は再試行できる。

## 性能と制限

未索引データの局面抽出は総手数に比例する。一度作成した後は一覧表示で局面を再生しない。集計は対象件数に比例する処理が残り、推定棋力のrating列も全対象分を保持するが、全件の棋譜本文・手順は取得しない。スクロール済みページは画面滞在中メモリに保持する。

初回索引完了までは一覧を待機する。バックグラウンド処理のためUIスレッドは占有しないが、初回待ち時間・索引容量は局面数に応じて増える。実機の性能値は別途測定が必要。

## 検証

実SQLiteで既存フィルタ・統計との一致、同時刻のページ境界、読込前ページのラベル、アカウント分離、分岐変更、削除、再起動、移行を検証する。本文取得の監視テストでは集計時0件、1ページ40件の取得を確認する。Composeテストではスクロールによる追加取得と未読込ページのラベル絞り込みを検証する。

`GameListReaderTest.benchmarkThousandGamesWhenRequested` はJVMシステムプロパティ `gameListBenchmark=true` 時に、固定シードで生成した100手の合法手順を1,000棋譜に保存し、旧全件照合、初回索引、索引後のページ・集計・候補取得を比較する。合成データ・PC上の値であり実機の待ち時間を保証しない。

計測だけ再実行する場合（`app/` 内）:

```sh
./gradlew :data:database:jvmTest -PgameListBenchmark=true --tests '*GameListReaderTest.benchmarkThousandGamesWhenRequested'
```

2026-10-04のPC/JVM測定では、旧全件照合約815ms、初回索引約4,040ms、索引後10回の中央値約3.9ms・最大約5.1ms。描画・ネットワーク時間は含まない。初回の永続索引作成は、旧処理1回より重い点に注意する。
