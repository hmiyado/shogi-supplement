# KIFヘッダ段級の実測結果

Issue #72 の調査として、2026-09-15（JST）に Supabase の `uploaded_games` を
個人を特定しない集計で確認した。

## 充足率

| 出典 | 棋譜数 | `user_rank` | `opponent_rank` |
|---|---:|---:|---:|
| 将棋ウォーズ | 19 | 18 (94.7%) | 18 (94.7%) |
| lishogi | 1 | 0 (0%) | 0 (0%) |
| その他 | 12 | 0 (0%) | 0 (0%) |
| 将棋クエスト | 78 | 0 (0%) | 0 (0%) |
| **合計** | **110** | **18 (16.4%)** | **18 (16.4%)** |

全体の充足率は低いが、将棋ウォーズに限れば十分に高く、対局時点の棋力ラベル
としてKIFヘッダを優先する根拠になる。空欄のサービスに申告棋力を補う用途では、
ヘッダ段級と申告履歴を混同しない必要がある。

## 表記

観測された `user_rank` は `初段` 14件、`三段` 2件、`二段` 1件、`4級` 1件だった。
`opponent_rank` は `二段` 13件、`三段` 2件、`1級` 1件、`5級` 1件、`初段` 1件だった。
今回のデータでは「3段」のような表記ゆれは確認できなかった。

## 判断

- 将棋ウォーズで値がある棋譜では、KIFヘッダ段級を対局時点の第一候補にできる。
- 全サービス共通の棋力帯ラベル採用順をこのIssueだけで変更しない。現在の実装では
  これらの列をラベル計算へ直接使う経路がなく、他サービスの観測数も不足しているため。
- #57 / #58 の棋力帯計算を実装するときに、`ShogiRank` への正規化と
  `ヘッダ段級 > 対局時点の申告 > 最後の申告` の優先順位を受入条件として引き継ぐ。

## 再現用の集計

```sql
select source_place,
       count(*),
       count(*) filter (where length(btrim(user_rank)) > 0),
       count(*) filter (where length(btrim(opponent_rank)) > 0)
from public.uploaded_games
group by 1
order by 1;
```
