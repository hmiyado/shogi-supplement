## 探索方式

AND/ORは詰み問題の構造を表す。現行の反復深化DFSとdf-pnは、別々の構造ではなく、
同じAND/OR問題に対する探索戦略の違いである。

| 方式 | 特徴 | 注意点 |
| --- | --- | --- |
| 反復深化AND/OR DFS | 手数の上限を順に増やす。短い局面や参照用の実装は比較的単純 | 同じ局面を繰り返し調べる。手順の順番で探索量が変わる |
| df-pn / df-pn+ | 証明数・反証数と閾値で探索先を選び、置換表で結果を再利用する | 局面合流、循環、GHI（経路履歴による結果の違い）、証明数の二重カウントへの対応が必要 |

df-pnのOR節点では証明数が子の最小値、反証数が子の総和になる。
AND節点では逆に、証明数が総和、反証数が最小値になる。
単にDFSをdf-pnへ書き換えるだけでは、十分に検証された実装にはならない。

KomoringHeightsはdf-pn+を用い、千日手・局面合流・二重カウントへの対策を持つ。
USIの詰将棋解答に対応する。ただし、既存実装であることだけで無条件に正しいとは扱わない。

## 詰みの存在と手数は分ける

やねうら王のdf-pnは、取得したPVが最短であることを保証しないと明記している。
KomoringHeightsも通常の詰み発見と、`PostSearchLevel=MinLength`による最短手数の確認を分けている。
「詰むと分かった」「返された手順がN手」「最短のN手詰め」は同じ結果ではない。

現行コードは、攻め側の初手をAIのPVに固定する。確認できるのはその候補手での詰み手数であり、
別の初手にもっと短い詰みがないことまでは確認していない。
局面全体に最短の「N手詰」を表示するなら、候補手限定の確認とは別の探索契約が必要である。

## このリポジトリで確認したこと

利用中のやねうら王ソースはcommit `717da871e7a620702b8b9433bd8f9f181710435a`に固定されている。
共有ソース一覧に`mate/mate.cpp`、`mate/mate_solver.cpp`があり、NNUE構成では
`USE_MATE_SOLVER`と`USE_MATE_DFPN`が有効になる。
Android・iOS・WASMは共通のソース一覧を参照するため、既存C++ソルバーの再利用を検討できる。

ただし、現在の通常NNUE探索へ`go mate`を送るだけで詰み専用df-pnを利用できるとは確認できていない。
専用の呼び出し経路・結果契約と、各プラットフォームでのビルド・動作確認が必要である。

## 破棄した試作の評価

- 全応手を調べて確認できた結果だけ採用する方針は妥当。
- 2,000ノード・31手・AI報告手数の上限に、実測による採用根拠がない。
- 詰み専用の追加テストは17件。810件はアプリ全体の成功数であり、詰み問題810問を解いた結果ではない。
- 既存ソルバーとの詰み／不詰・合法手・手数の比較を行っていない。
- 循環を証明に使わない実装は、正式な千日手・履歴の実装と同一ではない。
- 候補手の手数を局面全体の最短手数と同じに扱わないよう、表示契約を見直す必要がある。

## 採用前の検証案

1. 既存C++のdf-pnを実験用の呼び出し経路から動かし、KomoringHeightsを独立した比較対象にする。
2. 詰み／不詰／未確認と、手数上限／最短手数を結果型で分離する。
3. 双玉の実戦局面、必至型mate、合駒、打ち歩詰め、成・不成、攻め側の王手回避、反復局面を比較する。
   片玉の詰将棋データと双玉の実戦局面は、同じ前提として扱わない。
4. 解答が分かる問題集合で誤った詰み判定がないか検証し、同時に未確認率を測る。
5. Android・iPhone・WASMで処理時間・メモリ・キャンセル応答を測ってから探索予算を決める。

現時点ではdf-pnへ置換済みでも、既存ソルバーとの実測比較が完了した状態でもない。

## 2026-10-17 詰み専用構成の起動検証

アプリ固定版と同じソースで公式 `YANEURAOU_MATE_ENGINE` をmacOS/Apple Silicon向けにビルドした。通常NNUEの`go mate`は通常探索へ渡るため、専用df-pnの経路とは分ける必要がある。専用構成ではUSIの`checkmate`応答を確認できた。

16MB、Threads1、NodesLimit100,000、go mate 1000の起動実験結果:

| 局面 | 応答 | 確認 |
| --- | --- | --- |
| 近接金打ち | G*5b | python-shogiで合法・詰みを確認 |
| 飛車を打てる箱形 | R*5b | python-shogiで合法・詰みを確認。旧試作で扱ったR*5cの3手手順より短い別の初手がある |
| 平手初期局面 | nomate | この局面で王手を連続させる詰みなし。通常対局の勝敗を意味しない |
| 実戦wars_game3の69手後 | none | 99,989探索ノード。未確認であり不詰の証明ではない |

上記とは別にNodesLimit1でも飛車打ちの1手詰を返した。1手詰は1ノードで解けるため、この例は上限打ち切りの負例にはならない。各応答は約0.10〜0.11秒だが、専用USIループの待機も含む小標本の起動確認であり、探索予算の採用根拠にはしない。

通常NNUEのコンパイル済みオブジェクトへ直接APIをリンクした検証プログラムは、評価関数を読み込まずPosition::setを呼んだため初期化中に失敗した。これをdf-pnの失敗とは扱わず、評価関数に依存しない公式詰み専用構成で起動を確認した。通常エンジンに接続する場合は初期化と同時実行の条件を検証する必要がある。

`mate.h`の契約は、不詰MOVE_NULL、未確認MOVE_NONE、解答get_pvは最短保証なし。`set_max_game_ply`の深さ制限では範囲外を不詰扱いにするため、制限つきの不詰を無制限の不詰と混同しない。

当初は「詰みあり＋確認手順N手」を提案したが、メンテナの提案・承認により、最短手数を確認して「N手詰」を表示する方針へ変更した。[表示案](mockups/mate-confirmation-dfpn.html)もこの方針に更新した。通常探索への接続、負mateの全応手、最短手数、KomoringHeightsとの独立比較、端末/Wasmの予算・キャンセル検証は未実施。#107の実装完了とは扱わない。


## 2026-10-17 最短手数確認の試作

メンテナ承認: df-pnの解答を利用して、最短手数を追加確認する。製品の表示契約は「N手詰」を維持する。

`tools/probe_shortest_mate.py` は専用USIエンジンに対し、まず無制限の手数で詰みを探索する。PV長を目安にDepthLimit付きで詰みを再確認し、証明済みの上限を作る。その範囲で奇数手数を二分探索する。「N手以内で詰む」は上限について単調なので、N手以内の詰みとN−2手以内の不詰が証明されれば、最短N手と確定できる。PV長での上限確認が不詰なら、奇数手数の候補数を倍増して上限を探し直す。ユーザー指定max-depthを越えて探索しない。PV長は目安であり、全応手の最長抵抗を含む上限としては扱わない。PV長以内で解けなくても、既存の詰み証明を否定しない。

深さごとに探索木を作り直す32bitNodeSolverを指定し、深さに依存しない共有ハッシュは使わない。これは異なる残り手数の証明を混ぜないためである。手数制限は絶対game_plyへ変換される。探索打ち切りnone/timeout、制限内不詰nomate、最短手数確定を別の結果にする。上限確認や二分探索の問い合わせが一つでも未確認なら、手数は未確定とする。

公式固定ソースの `source/testcmd/mate_test_cmd.cpp` にある最初の詰将棋用局面へ先手玉9九を加えた次の双玉局面で検証した:

```text
3sks3/9/4+P4/9/9/+B8/9/9/K8 b S2rb4gs4n4l17p 1
```

- DepthLimit1: nomate。DepthLimit3: `9f5b 4a5b S*4b`。独立したpython-shogiの合法手生成を使う有限AND/OR全探索でも、1手不詰・3手詰を確認した。
- 絶対手数を41に変えても、最短3手を確認した。
- 盤面を180度回転し先後を交換しても、最短3手を確認した。これは攻め方が後手の場合であり、受け方手番の負mate確認とは異なる。
- 同局面のNodesLimit1はnoneとなり、最短手数を表示しない。
- 制御ロジック11件と実エンジン4件の計15テストで、二分探索の途中・上限確認の未確認、PV長より長い抵抗、偶数の手数上限、1手詰、手数予算不足、none/timeoutとnomateの区別を確認した。1〜31手の全16閾値とPV長目安1〜33の組み合わせ528通りで、最短手数と問い合わせの重複がないことも確認した。
- 模擬31手詰の問い合わせ回数は、無制限探索込みで昇順17回から二分探索6回（0,31,15,23,27,29）に減った。実エンジンの3手詰は両方式とも3回で、実行速度が改善したとの結論は出していない。

再現にはpython-shogiと、固定ソースでビルドしたYANEURAOU_MATE_ENGINEが必要:

```sh
YANEURA_MATE_ENGINE=/path/to/yaneura-mate python3 -m unittest discover -s tools -p test_probe_shortest_mate.py
python3 tools/probe_shortest_mate.py --engine /path/to/yaneura-mate \
  --sfen '3sks3/9/4+P4/9/9/+B8/9/9/K8 b S2rb4gs4n4l17p 1' --max-depth 9
```

この試作は採用前の検証用で、アプリへ接続していない。max-depth、nodes、millis、hash-mbの値は実験条件であり、製品の予算として採用していない。通常エンジンとの接続、受け方手番、反復局面・履歴、KomoringHeightsとの独立比較、各プラットフォームの性能とキャンセル検証は引き続き必要。


## 2026-10-17 アプリへの統合

通常NNUEエンジンの最終結果へ、上記の二分探索を接続した。現在の実装契約と保存互換性は[詰み確認](mate-verification.md)に記載する。前節までの「製品未接続」は各実験時点の状態である。

通常NNUE構成のmacOSバイナリと、WasmのSIMD/非SIMD両方で、1手詰・3手詰・受け方手番の2手を確認した。macOSでは返された全確認PVをpython-shogiで合法性・終端の詰みを検証し、実戦69手後は未確認の数値表示になることも確認した。通常解析込みのmacOS実測は1手例約0.04秒、3手例約1.12秒、受け方例約0.001秒であり、df-pn単独の時間ではない。WasmのNode実行は通常初期局面を含む4局面と初期化込みで約4〜6秒。スマートフォン実測への外挿はしない。

レビューの時間制限指摘を受け、df-pnの探索ループ内でも期限を確認するようにした。期限はスレッドローカルで、呼び出し後に元の値へ戻す。500msは次の探索ループへ戻った時点での打ち切りであり、メモリ確保や一つの局面展開の途中を強制中断する制限ではない。準備スクリプトも、ヘッダのみの変更を再コンパイル判定へ反映する。

負mateの非王手局面を確認対象に含めるレビュー指摘は採用しない。今回の契約は連続王手による詰みであり、王手されていない受け方の必至をN手詰とは表示しない。対象外を不詰の証明とはせず、未確認にする。


追加確認: 固定版のmate_repetitionは千日手や持駒の優越関係から勝ちを結論する経路を持つ。N手詰の確認では、この近道を用いた問い合わせは詰み・不詰いずれの答えでも未確認に戻す。これにより二分探索の誤った下限にも使わない。返却PVもC++内で合法性・連続王手・終端の詰みを確認する。3手例の前に合法な玉・銀の往復 `9i8i 4a3b 8i9i 3b4a` を付けた履歴では、数値9999のまま手数に昇格しないことを通常エンジンで確認した。これは履歴依存の結果を保留する検証であり、当該局面が不詰だという結論ではない。
