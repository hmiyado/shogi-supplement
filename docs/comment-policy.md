# コメント規約

コード内コメント（KDoc・行コメント・ブロックコメント）の方針。
機械チェックは `tools/comment_lint.py`、レビュー手順は `.claude/skills/self-code-review`。

## 原則

**コードは How ／ テストコードは What ／ コミットログは Why ／ コメントは Why not**。

コードは動作を語り、コミットログは変更理由を語る。両者が語れないもの——
**そのコードを読んでも分からない制約と、選ばなかった選択肢の理由**——だけがコメントに残る。

## 書いてよいコメント

- **Why not**: なぜ別のやり方を採らないか。「〜にしない理由:」の形で、却下した案と理由を書く
- **コードから読めない制約・不変条件**: 外部仕様の要求、ライブラリの制限、
  他システムとの一致が必要な値、スレッド安全性の前提など、破ると壊れるが
  コード上は見えないもの
- **非自明な入出力の契約**: 引数・戻り値が取りうる値と意味（KDocの `@param` / `@return`）。
  ただし名前から自明なものは書かない
- **テストコードの What**: そのテストが何を保証するか（テストは仕様の記述であるため、
  他のコードとは扱いが違う）

## 書いてはいけないコメント

### 1. What の説明（コードの言い換え）

```kotlin
// NG: コードを読めば分かる
/** 現在の状態を返す。 */
val state: State
// NG: セクション見出し
// ── 状態の定義 ──
```

### 2. 利用される側の事情

呼び出し元の都合を書かない。**対象自身の契約として書き直せるなら書き直し、
書き直せないなら削除する**。

```kotlin
// NG: 「呼び出し側はその間サーバー解析へ向かう」
// OK: 「準備状態は state で公開する」（対象自身の契約として書く）
```

デザイン・レイアウト側の事情を文言定数にコメントするのも同類
（「この文言はボタン幅に収まるため8文字以内」など）。

### 3. 陳腐化する経緯・当時の判断

レビュー指摘・承認状況・検証状況・実装予定・過去の実装は、コードが変わっても
コメントだけが残って嘘になる。**変更の経緯はコミットログが持つ**。

```kotlin
// NG: 「レビュー指摘で廃止」「承認済みモック通り」「検証済み」
// NG: 「旧実装では〜だった」「〜する予定」「ベータでは〜」
// NG: コミットSHA・タスク名・人名への言及
```

### 4. 他ファイルへの安易な参照

責務の委譲先を示す参照（「判断ロジックは X が持つ」）は書いてよい。
**利用側を示す参照**（「X から呼ばれる」）は書かない。参照はファイルが動くたびに
腐るため、必要最小限にする。

### 5. コメントによる同期指示

複数箇所に複製したリテラルを「変更時は両方直す」で守ろうとしない。
コメントは実行されないため乖離を防げない。

```kotlin
// NG: 「KentoAssetCache.swift と同じキー文字列を使うこと（変更時は両方直す）」
// OK: 単一の定義に集約して参照で共有する（言語境界はフレームワーク経由の参照で解決できる）
// OK: 参照共有が不可能なら、一致を検証するテスト・ビルドフェーズを用意する
```

検証をテストやビルドフェーズに落としたあと、**その存在を対象側のコメントで案内しない**
（違反すれば機械が止めるため、コメントは冗長）。

### 6. 利用側文脈の命名

`fallback`・`demo` など「どう使うか」を表す語をクラス名・ファイル名・変数名に入れない
（切替ポリシーを持つ合成箇所の命名のみ可）。

## 分量の上限（機械チェック）

`tools/comment_lint.py` が変更対象のKotlinファイルを検査する。**個別の長さ**と
**ファイル全体の総量**の両方を見る（長さだけでは、上限内の説明を大量にばら撒く形が
素通りするため）。実測は2026-08-13時点（プロダクション256ファイル・28,858行。
総量は60行以上の128ファイル）。

| 観点 | 上限 | 実測（中央 / p90 / 最大） |
|---|---|---|
| クラス・interface・objectのコメント | 10行 | 4 / 14 / 28 |
| 関数・プロパティのコメント | 5行 | 1 / 7 / 34 |
| 処理中のインラインコメント | 3行 | 1 / 4 / 17 |
| 総量: コメント行 / 宣言数 | 2.5行 | 1.89 / 4.10 / 13.00 |
| 総量: インラインコメント行 / コード行 | 0.08 | 0.00 / 0.07 / 0.86 |

総量の分母（宣言数）は、**名前を持つ宣言＝トップレベルとクラスメンバ**を数える
（`class` / `interface` / `object` / `fun` / `val` / `var`）。関数本体の中の変数は
数えない——作業用の変数まで分母に入れると、処理が長い関数を持つファイルほど
規制が緩くなるため。説明の要らない宣言も分母に入るので、上限2.5行は
「説明が要る宣言にはしっかり書き、要らない宣言には書かない」を想定した値になる。

**Why not コメント行 / 総行数で総量を測る**: 宣言1つに1行ずつ説明を付ける健全な
書き方（文言定数の一覧など）でも比率が上がり、良い書き方を罰してしまう。実測でも
文言定数ファイル（841行・宣言133個）はこの旧指標では違反だが、宣言あたりでは
0.93行と中央値以下だった。

上限を超えたら、まず**消せないか**を考える。「元からあった」は残す理由にならない
（実例: 再試行するステータスの列挙はコードの言い換え、既定値の意味の説明は
シグネチャと重複していた）（上の「書いてはいけない」に当たらないか）。
消せない制約が本当に長いなら、コメントではなく設計ドキュメント（`docs/`）へ出して
コードからは1行で参照する。

### 既存コードの扱い

規約制定時点で上限超過が525件ある（大半は規約が固まる前に書かれたもの）。
**コメントは全体として減らしていく方針**のため、既存分も修正対象とする。ただし
一括修正はせず、**触ったファイルだけを直す**運用にする
（`--staged` / `--diff` は変更対象のみを検査する）。全体の分布は
`python3 tools/comment_lint.py --stats app` で確認でき、上限は分布の改善に応じて
下げていく。

## 実行方法

```sh
python3 tools/comment_lint.py --staged      # ステージ済み（pre-commitフックが実行する）
python3 tools/comment_lint.py --diff main   # mainとの差分（CIが実行する）
python3 tools/comment_lint.py --stats app   # 分布の確認（上限見直し用）
```
