# 解析来歴と再解析の扱い

1.14 の解析基盤 issue に対する、実装済みの安全な範囲と未決定事項を記録する。

## 実装済み

- サーバーの解析応答に含まれる `engine_meta`（エンジン版、評価関数ハッシュ、nodes、Threads、MultiPV、USI_Hash、FV_SCALE）を、リモート解析結果からローカルの `game.engine_meta_json` まで渡して保存する。
- `uploaded_games.engine_meta` を追加し、アップロード・一覧/詳細取得で来歴を保持する。既存行と旧クライアントは `NULL` のまま扱う。
- サーバーの新規キャッシュキーには、エンジン成果物だけでなく固定解析条件も含める。同じエンジン版・評価関数でも条件が異なる結果を新条件の結果として返さない。
- 既存の版不明データは削除・推測・再計算せず、`engine_meta_json = NULL` として「来歴未収録」と扱う。

## まだ自動化していないこと

同じ `content_hash` のローカル棋譜は、現在も既存 game を返して再解析しない。来歴を保存できるようになっただけでは、旧レポート・ドリル履歴・学習履歴を安全に移し替える方針までは決まらないため、再解析の導線と上書き処理は追加していない。

サーバーでは条件をキーに含めたため、新しい条件のキーは旧条件のキャッシュと分離される。移行期間中は、旧bare hashと旧`engineRev|evalSha` hashも検索するが、`engine_meta`の全条件一致と`result_json`の正常性を確認できた完了済みジョブだけを quota 判定前に再利用する。旧RUNNINGは旧workerとの排他を証明できないため引き継がず、通常の新キー処理へ進める。これにより条件の違う結果の取り違えと、旧行の無制御なresetによる二重実行を防ぐ一方、旧RUNNINGが生きている移行直後には重複実行になり得る。このケースの待機・昇格はDBのlease/fencing設計が決まるまで保留する。

## 方針決定が必要な項目

- 解析条件 ID を、固定の `engine_meta` から導出するか、明示的な版文字列として管理するか。
- 旧結果を表示し続けるか、条件不一致として再解析を促すか。
- 再解析時に同じ game を上書きするか、世代を分けて旧レポートとドリル解答履歴を残すか。
- 学習履歴とドリル問題の安定 ID を `content_hash + ply` 等で定義するか。
- 旧キャッシュを quota 非消費で移行できる管理操作を用意するか。
- 旧キー検索をどのリリースまで残し、旧RUNNINGを待機・昇格するlease/fencingを導入するか。
