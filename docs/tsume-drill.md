# 次の一手問題の詰将棋モード

## 操作

[ホームの構成案](mockups/tsume-drill.html)に従い、「今日の1問」に「次の一手」と「詰将棋」の開始ボタンを横に並べる。
タブや開始前の確認画面は追加しない。問題画面には種類の切替を置かない。
「次の問題」は最初に選んだ種類を維持する。別の種類を始めるときはホームへ戻る。

詰将棋も既存の次の一手と同じく初手を判定し、続けて入力した読み筋は既存の方法で保存する。
詰みまで全手順を解答する専用ルール・最短手数の正解条件は追加しない。
正誤判定、正解表示、検討、解答履歴、周回の優先順位は既存の次の一手と共通である。

## 出題対象

DB検索時に出題判定（◎／○）と`mate_verified != 0 AND missed_mate_in > 0`を適用し、詰将棋の対象にする。
DB変換時に`mate_verified = 0`の値はnullへ正規化されるため、旧解析や未確認の「N手勝ち」は含めない。
これは実戦から抽出した詰みの局面であり、創作詰将棋の作品要件を保証するものではない。

対象がない場合はホームの詰将棋ボタンを無効にして説明する。
開始後の削除・再解析などで候補がなくなった場合は詰将棋の空状態を表示し、通常問題へ自動で切り替えない。
通常の次の一手では、従来どおり詰みを含めたすべての出題候補を扱う。

## 状態と保存

AndroidとiOSは画面遷移に選んだ種類を含め、対応する共通ViewModelへ渡す。
候補はDB側で解答回数昇順、◎／○順、優先度降順、同点ランダムの順に並べ、`LIMIT 1`で次の1問だけを返す。
同じ読み取りトランザクションで対象の総件数と選択された問題の解答回数を数値として取得する。
全候補レコード・全問題の解答回数マップをアプリへ読み込まない。
ホームの詰将棋ボタンの可否は`EXISTS`で確認する。
件数の集計と出題順位の計算はDB内で対象データを処理するため、問題数と無関係な定数時間を保証するものではない。
解答履歴は同じ問題IDへ保存し、通常と詰将棋で履歴を分割しない。
新しいDB列・設定の永続化・通信の項目は追加しない。

## 検証

DBを経由して通常・確認済み詰み・未確認mate・ゼロ・負値を混ぜ、候補と件数を確認する。
次問への移動、解答履歴の保存、候補なし、ホームの可否表示、2つの開始先を検証する。
320dpの通常・空状態・暗色の画面と既存ホームの画像比較を確認する。
Android本体とiOS／Web向け共通UIをコンパイルする。
