# サーバー検討専用候補の同一実時間比較

実施日: 2026-09-27。[固定したプロトコル](engine-study-match-protocol.md)と[機械可読結果](verification/engine-study-match.json)を参照。

後続の[worker検証](engine-study-worker-validation.md)で、検討専用の条件分離と実エンジンのローカルHTTP経路を追加確認している。Linux実行の状態も同文書へ記録する。

## 結論

**この短時間・macOSの条件では、9.80＋Aobaの対局上の優位性を支持する予備結果が得られた。サーバー検討専用の候補として検証を続ける根拠になる。**

通常解析の棋力推定精度とは別の結果であり、正式採用・本番配信の確認ではない。前回の固定ノード比較でAobaが遅かったことだけを、検討専用の採用を見送る理由にはしない。

## 対局結果

macOS 27.0 (26A428)、arm64。9.40＋Háo対9.80＋Aoba。32種類の開始局面から先後を交換した64局、1手200ms、Threads 1、Hash 128MB、MultiPV 1。開始局面は279対局から事前に固定した32対局の24手目で、32局面すべて異なる。途中結果を理由に標本や終了条件を変更していない。

| 結果 | 局数 |
| --- | ---: |
| Aobaの勝ち | 40 |
| Háoの勝ち | 23 |
| 未判定 | 1 |

決着した63局はすべて詰み。1局は開始局面後320手で打ち切り、両玉が相手陣に入っていた。評価値を根拠に勝敗を補完せず、引き分けにも数えていない。全64局の7,957着手と、生出力中のPV60,922手の合法性、履歴・最終盤面・勝者・終了理由を再検証して成功した。

未判定を候補の負け／勝ちとした得点率の範囲は**62.5〜64.1%**。完全判定を前提とした事前定義の主解析は未成立なので、その区間推定は出していない。

補助的な感度分析では、未判定をAobaの負けと置いても、32先後ペアを単位としたbootstrap 95%区間は**51.6〜73.4%**だった。未判定をAobaの勝ちとした場合は53.1〜75.0%。seed=101、20,000回のpercentile区間。この補助集計は打ち切り発生後に追加したもので、事前に決めた主解析と区別する。

下限が50%を超えたことは候補を支持するが、32ペアの小標本・特定コーパス・1手200msの予備試験である。元対局のプレイヤー重複、似た戦型などの依存、OS負荷・温度は完全に制御していない。長時間対局、一般的な棋力差、公称レートには換算しない。ソース本体と評価関数を同時に変えているので、改善の寄与を個別には分離できない。

## 時間条件と複数候補

| 構成 | 対局時の中央値 | 対局時のp95 | 最大 |
| --- | ---: | ---: | ---: |
| 9.40＋Háo | 200.112ms | 200.876ms | 203.597ms |
| 9.80＋Aoba | 200.309ms | 201.341ms | 204.181ms |

両者とも指定時間の10%以上の超過は0回。送信からbestmove受信までのホスト側実測で、ロード・readyok・HTTP待ち・保存は含まない。計測中は他の重いテストやビルドを実行していない。ごく小さい実時間差もあるので、完全に同一のCPU時間を測ったとは扱わない。

対局後、同じ32局面で両構成を**1局面1秒・MultiPV 3**で逐次実行した。64探索すべてで3候補を取得し、bestmoveとPV内7,579手は合法、最終候補の先頭手の重複は0件。p95はHáoが1.000596秒、Aobaが1.001262秒。このプローブは複数候補の動作確認であり、候補の正解率やUI・HTTPの動作確認ではない。

## サーバー検討専用で残る確認

今回進んだのは、同じ時間予算での候補の有用性とネイティブ動作の証拠。次の範囲はまだ確認していない。

- native Linux x86_64での起動・連続解析・停止・実時間・ピークメモリ・初回ロード・費用。macOS値をCloud Runへ換算しない。
- サーバーが選ぶ専用profileでAobaのFV_SCALE=40を実行条件・来歴・キャッシュ識別に通し、通常解析の20と混ざらないこと。現行workerは20固定なのでファイルだけの差し替えでは成立しない。
- 実際の検討APIから複数候補を取得・保存し、古いクライアントとの混在、取消・遅延結果、quota、手動rollbackを確認すること。クライアントに任意の探索条件を選ばせる方式は採らない。
- 実際に提供する時間・ノード上限での有用性と待ち時間。本番workerの現在のエンジン版も、今回の比較元とは別に確認が必要。

この範囲には通常解析の棋力推定係数の再学習や、候補エンジンのAndroid/iOSへの同梱は含めない。採用範囲を拡大するときに別途評価する。移行計画の正本は引き続き[Issue #101](https://github.com/hmiyado/shogi-supplement-research/issues/101)。製品設定、デプロイ、Issue状態は変更していない。

## 再現と保存

対局実行はプロトコルのコマンドを使用する。後処理:

```sh
python3 tools/probe_engine_study.py \
  --manifest /path/to/study-match/games/manifest.json \
  --output /path/to/study-match/study-recheck --milliseconds 1000
python3 tools/summarize_engine_matches.py \
  /path/to/study-match/games --output /path/to/study-match/summary-recheck.json
python3 -m unittest discover \
  -s tools -p test_match_engine_profiles.py -v
```

使用したpython-shogiは1.1.1。打ち切り・千日手・先後交換時の投了・違法手と勝者改変の拒否を4テストで確認した。生ログと入力履歴は`/path/to/study-match/`に保存し、集計JSONにはバイナリ・評価関数・実行スクリプト・各生ログのSHAを残している。個別の元棋譜はgit管理対象に含めていない。
