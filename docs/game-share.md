# 棋譜の静的URL共有

レポートの共有メニューから棋譜全体と表示局面を送る。既存の画面共有も残す。
対局者名は送り主視点の「自分」「相手」で表示する。

## 発行と閲覧

- `POST /v1/game-shares` のみWorkerへ送る。JWT・設定済みならApp Check・既存の更新ポリシーで認証する。IPの履歴を保持する独自の回数制限は追加しない。
- 元棋譜はサーバーへ同期済みである必要がある。所有者とcontent hashで `uploaded_games_v2` を優先し、旧 `uploaded_games` も扱う。同期前・別所有者の棋譜は409となる。
- 保存するのは検証済みの開始局面・本譜・選択局面・必要な分岐・手番・表示向き・勝敗と許可された終局理由だけ。名前、日時、コメント、評価、元ファイル名、所有者IDは公開しない。
- IDは暗号学的乱数128bitをURL-safe Base64化する。パスは `game-shares/<id>.json`。発行ごとに別IDを使い、上書きしない。送信結果が失われた場合、再試行で別URLが作られる場合がある。
- WebのURLは `kento.html?game=v1&id=<id>`。JSONはSupabase Storageの `/storage/v1/object/public/game-shares/<id>.json` から直接取得する。閲覧にWorker・JWT・App Check・認証ストアは不要。
- 公開専用バケットには一般ユーザー向けの一覧・書き込みポリシーを作らない。公開GETが可能でも一覧は取得できないことをHTTPでも検証する。
- 共有一覧、公開切替、個別の共有停止、Worker経由の閲覧APIは設けない。

以前の局面URLフラグメントの読み込みは維持する。新しい棋譜共有は本番未導入のため、旧実装のDB/APIを公開互換経路として維持しない。

## 元棋譜・アカウントの削除

予約時に元棋譜をロックして、正確な保存テーブルと所有者・content hashを非公開の対応表へ記録する。
元棋譜をサーバーから削除すると対応表も削除され、同じトランザクションでStorage削除キューへIDが残る。
アプリが使う削除RPCの世代削除記録にも連動する。旧テーブルに実体が残っていても、削除済みの棋譜は再発行しない。発行予約は既存の世代同期と同じ所有者・棋譜単位のロックを使う。
アカウント削除でも同様。端末内だけの削除は対象外。

Storageの実ファイルはSQLで消さず、Storage APIで削除する。ジョブはキューを時刻順に100件ずつ処理し、失敗した処理は再試行する。
10分以上完了しない発行予約も削除対象にする。HTTP送信・完了記録の途中でWorkerが終了しても予約から回収できる。
元棋譜の削除とアップロードが競合した場合は完了記録が失敗し、発行元にURLを返さない。
削除記録は所有者の外部キーを持たず、アカウント削除後も残る。タイムアウト後に遅れて到着するアップロードを取りこぼさないため、削除成功後も24時間の確認期間中は記録を保持する。期間終了後にもう一度削除できたら記録を消し、失敗した記録は残して再試行する。

削除は非同期で即時失効ではない。通常の定期実行は5分間隔で、キュー待ち・再試行・遅延アップロードによって時間がかかる。
JSONのキャッシュは60秒。受信者が保存したコピーは消せない。

## 配布

1. 新しいDBマイグレーション・Storage専用バケットを準備する。
2. 新Workerを配布する。既存の解析・引き継ぎAPIと設定は維持する。
3. Terraformの `game_share_cleanup_image` に新Workerのdigest固定イメージを設定し、削除JobとCloud Schedulerを有効にする。空文字列なら両方作成しない。Job引数は `--cleanup-game-shares`、必要環境変数は `SUPABASE_URL` とservice roleのみ。HTTP公開エンドポイントは使わない。
4. SchedulerからのJob実行、削除失敗の再試行、アカウント削除後の実ファイル削除を確認してから新クライアント/Webを配布する。

JobとSchedulerを未設定のまま機能を公開しない。旧Workerへ戻すと発行はできなくなるが、公開済みJSONの閲覧はStorageで継続する。削除Jobは継続する必要がある。

## iOS実機からのLAN確認

開発用のSupabase・Worker・静的ページをMacのLANアドレスで公開し、iPhoneを同じネットワークへ接続する。
通常のDebugアプリの「設定→デバッグ→接続先」で、本番またはLAN内の開発環境を選ぶ。
LANではMacのWeb配信URLを入力して保存し、アプリを終了して起動し直す。接続先ごとに棋譜DB、認証セッション、引き継ぎ用の鍵を分け、本番の保存先は従来のまま維持する。

MacのWeb配信ルートに `development-config.properties` を置く。以下の4項目だけを公開する。

- `SUPABASE_URL`: LAN内のSupabase URL
- `SUPABASE_KEY`: ローカルSupabaseの公開anonキー
- `GAME_SHARE_API_BASE_URL`: LAN内のWorker URL
- `GAME_SHARE_WEB_URL`: LAN内の `kento.html` URL

アプリは入力URLと同じプライベートIPv4ホストのHTTP接続先だけを受け入れる。転送は追わず、キーのroleがanonであることを確認する。service role・署名秘密鍵・本番用設定ファイルは配信しない。LANではサーバー解析URLを設定せず、エンジン同梱Debug版は端末内で解析する。

ReleaseはDebugの保存値を読まず、従来のバンドル設定とデータ保存先を使う。HTTP許可はDebugのみ。LAN選択時は本番のFirebase・App Check・Sentryを起動しない。開発WorkerのApp Check無効化は本番設定には反映しない。ローカル認証も非対称署名/JWKSで検証する。

共有ページの手数表示を押すと、アプリと共通の棋譜一覧を開く。初期局面を含めて選択でき、長い本譜を横スクロールする必要はない。検討の分岐移動は従来の操作を維持する。
