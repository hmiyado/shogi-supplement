# 詰み確認

通常AIのmateは手数と確認状態を保持し、未確認なら「+N手勝ち」「−N手負け」と表示する。最短詰み手数としては扱わない。やねうら王の既存df-pnと手数上限の二分探索で確認できた結果だけScore.Mateのverifiedをtrueとする。未確認でも通常探索の手数を保持する。

## 探索契約

攻め方は合法な王手から選択し、受け方の全ての合法な王手回避に詰みがあることを証明する。最初に手数無制限で詰みを発見し、そのPV長を目安に手数制限付きで上限を証明する。PV長が全応手の最長抵抗を表すとは仮定しない。上限不足なら、候補数を倍増して上限を探し直す。

証明済み上限と不詰の下限の間を二分探索する。攻め方手番は奇数手、受け方手番は偶数手を調べ、N手以内の詰みとN−2手以内の不詰から最短N手を確定する。未確認を詰み・不詰のどちらにも振り分けない。千日手・持駒の優越関係の近道を一度でも用いた探索結果も未確認とする。不詰側の結論も除外することで、誤った下限から最短手数を確定しない。

受け方手番は、王手されている局面について全合法応手を調べる。各応手後の攻め方探索を共通の手数上限で確認する。王手されていない負mateは、必至を詰みと取り違えないよう未確認とする。双玉以外も未確認とする。

PV1は局面全体の最短手数と、その証明手順へ更新する。確認手順の初手が通常探索と異なる場合はbestmoveも更新する。正のPV2以降は、その候補の初手を固定して、全ての受けに対する最短手数を確認する。負のPV2以降は現時点では未確認の勝ち／負け手数として扱う。検討の局面ラベルは局面全体の証明を優先し、初手固定候補の手数を局面全体の最短手数に流用しない。最善手が変わって候補が重複した場合は重複を除く。

## 実装と予算

[共有C++実装](../app/engine/mate/verified_mate.h)を[ソース準備](../app/engine/prepare_mate_verification.py)で固定版へ適用する。Android・iOS・Wasm・Workerのビルド経路から同じ実装を利用する。通常探索の途中は未確認mateを出し、bestmove直前に確認済みの最終結果を出す。返すPVは合法手と連続王手を辿り、終端が実際の詰みであることも確認する。

1局面の候補全体で100,000ノード・500ms・16MiBを共有する。手数は攻め方63手、受け方62手まで確認する。32bitNodeSolverは各問い合わせで探索木を作り直し、残り手数に依存しない共有ハッシュを使わない。

時間は探索ループ内で確認する。メモリ確保・一つの局面展開の途中を強制中断するものではない。上限に達しても証明済みでない結果を採用しない。Wasmのキャンセルは従来どおりWorker終了、サブプロセスはプロセス終了を利用する。iOSのプロセス内エンジンでは同期解析終了まで待つ既存の制約がある。

## 通信・保存

USIには`mateverified`、JSONには`verified: true`を明示する。確認情報のない旧エンジン・旧Worker・旧Wasmのmateは未確認の勝ち／負け手数として扱う。旧クライアントは確認フラグを区別できないため、新しい表示にはアプリ更新が必要。Workerのエンジン来歴は`+dfpn3`、Wasm資産は`yo-717da87-p4`として旧解析キャッシュと分離する。

DBの`27.sqm`で局面評価と悪手レポートへ確認情報を追加する。旧データの手数は削除せず、未確認として読み出す。旧mate 0の符号は局面の手番から判断する。旧レポートの詰み手数・手数付き問題名・注記も、確認済みであるかのように表示しない。再解析後は確認結果を保存する。position_evalのmate_verifiedはbit 2を独立フラグ形式の識別に使い、bit 0が第一候補、bit 1が第二候補。旧値1は両候補確認済みとして読む。
